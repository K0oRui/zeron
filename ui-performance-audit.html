Performance audit

Zeron UI: where the time actually goes

A read of the desktop UI (crates/ui, gpui) and the loading path that feeds it, focused on what is slow now and what is worth fixing. Every finding cites the code.

Repo zeron Revision a25d3a26 Date 2026-11-05 Scope startup, loading, transcript, sidebar, palette, diff, history Method source trace + existing perf docs

This codebase is already performance-obsessed. The transcript is genuinely virtualized with memoized row heights and tail-only relayout, markdown re-parses only the streaming tail, syntax highlighting runs on a background executor, the sidebar row model is fingerprinted and cached, workspace search runs on a real index, and there are measured reports for composer, sidebar, idle, scroll and memory. Most of the obvious wins are already banked.

The remaining cost is concentrated in three places. Startup blocks the main thread on font enumeration and the engine boot, streaming rebuilds the entire row model on every token, and the whole shell repaints on every state change. Those three multiply everything else. Fix them and the rest of the list here stops mattering.

01Startup and loading, phase by phase

The first painted frame is cheap on purpose, it is just the splash. Time to a usable shell is dominated by the engine, not by gpui. Red dots mark phases that block the main thread or the critical path.

Main-thread setup before any window

crates/ui/src/lib.rs:183-227

Settings JSON load, keymap migration, font registration, theme library load, appearance and history init all run synchronously inside app.run. Font registration enumerates every installed system font and parses each face with ttf_parser (see issue 1). Unbounded by app data, bounded only by how many fonts the machine has.

Shell construction and keymap rebuild

crates/ui/src/shell.rs:2747-3187

Shell::new builds the transcript, composer, voice controller, three orbs, the sidebar pane and the session card, plus roughly 40 focus handles. apply_keymap clears all bindings and rebuilds them twice (once for base, once localized). All synchronous, before the first frame.

First frame: splash only

crates/ui/src/shell.rs:15218

The loading gate renders the shell root with the splash overlaid. Nothing heavy paints here, which is deliberate.

Background engine launch and attach poll

crates/ui/src/state.rs:419-461

On the default path the app spawns the background engine and polls the IPC port every 150 ms for up to 20 seconds. Two earlier probes (750 ms and 500 ms) run first. A cold engine start waits for the child to open SQLite and begin serving.

Engine assembly before the port serves

crates/engine/src/workspace_host.rs:250-375

DocsStore::open runs WAL setup and a blocking checkpoint, then WorkspaceHost::open loads the whole workspace registry snapshot in one shot (with a one-time legacy Loro import on old profiles) and writes it back before returning. Boot time and memory scale with workspace size.

Ready, then a fixed splash fade

crates/ui/src/shell.rs:3667-3681

Once the engine reports ready the splash fades over about 680 ms (150 ms delay plus a 500 ms run). A fixed cost on top of the real load.

Opening a chat

crates/engine/src/doc_host.rs:56-60

Warm docs reopen in about 11 ms; the watch prepares rows on the background executor and installs them on the foreground. For the 21 MB whale transcript that is about 806 ms background prep and 12 ms foreground install, per docs/whale-ui-responsiveness.md.

02The biggest issues

Ranked by likely impact. Severity reflects both how much time it costs and how widely it is felt. Items the project has already documented as deliberate tradeoffs are marked as such rather than presented as bugs.

01

System font enumeration and parsing on the main thread at startup

High
crates/ui/src/typography.rs:348-379 · called from crates/ui/src/lib.rs:190
What
installed_families_with_latin_metrics() builds a fontdb::Database, calls load_system_fonts(), then parses every installed face with ttf_parser::Face::parse to test for the m glyph and fixed-width advances.
Why slow
Work is O(installed fonts) and entirely on the UI thread before the first window. A machine with hundreds of fonts pays it on every launch. It is not measured in any of the existing reports.
Fix
Move the enumeration to background_executor and publish the availability map when ready, or parse lazily the first time a family picker opens. The embedded Geist faces can register immediately; only the system scan needs to move.
02

Engine boot loads and rewrites the whole registry before serving

High
crates/engine/src/workspace_host.rs:250, 262-294, 375 · crates/engine/src/lib.rs:249-299
What
WorkspaceHost::open loads the entire registry snapshot, optionally imports a legacy Loro doc and reads every row, then persists the snapshot back synchronously before returning. It sits behind a 20-second polling loop (crates/ui/src/state.rs:419-448) that only resolves once the engine serves.
Why slow
Boot time and peak memory scale with total workspace size (chats, spaces, devices, history). The splash hides it, but it is the real "loading everything" delay, and it happens on both cold app start and engine replacement.
Fix
Serve the port before the registry is fully hydrated and stream the registry to the UI as it loads, or make the boot-time persist_snapshot conditional on the snapshot actually being dirty. The legacy import can run in the background after first serve.
03

Every streamed token rebuilds the entire transcript row model

High
crates/ui/src/transcript.rs:5225-5260, 5670-5706 · crates/ui/src/state.rs:1980-1983, 4818-4831
What
sync iterates every entry and rebuilds new_rows for all of them, then diffs the full vector with diff_rows, even though only the tail is spliced and remeasured. rows_for additionally clones each cached entry twice (cached.rows.clone() and an unconditional rows: rows.clone()).
Compounding
On a text-append frame apply_transcript_frame removes prepared_transcripts[selected] before emitting, and the watch re-inserts it only afterward. So the emit-driven sync sees no prepared rows and falls back to rebuilding on the UI thread. The subagent path inserts prepared first, so it does not pay this.
Why slow
Cost is O(total rows) per token. A 2000-row conversation re-clones roughly 2000 rows on every delta, at the streaming cadence. Background preparation exists to prevent exactly this and is being discarded on the hot path.
Fix
Insert prepared before the update emit (match the subagent ordering), and make sync a tail-only update when the entry list is append-only. Avoiding the second clone in rows_for is a cheap follow-up.
04

Any state change repaints the whole shell, transcript and sidebar

High
crates/ui/src/shell.rs:2748, 2928, 2934
What
Shell observes AppState and calls cx.notify() on any change; Shell also notifies the transcript, which notifies the sidebar pane. Writes are change-gated, but a change has no granularity. The only targeted signal is TranscriptTextChanged for text-only appends.
Why slow
This is the multiplier. A settled tool call, a presence heartbeat, a pin, a resize or a hover all walk the full shell render. Documented as a known cost in docs/performance-sidebar.md, not a regression.
Fix
Hard to dismantle fully in gpui, but the highest-value move is a per-row sidebar notification channel (an event that names the changed chat), so a status flip does not re-run the whole list. The palette and other panes could subscribe to narrower signals too.
05

Sidebar rebuilds its full row model once a second and does O(n) work per frame

High
crates/ui/src/state.rs:5034-5124 · crates/ui/src/shell/spaces.rs:6760-7336
What
The row-model cache key is a fingerprint that hashes the current clock second plus every chat, session, space, device and change-request snapshot. While the selected chat is working, shell_clock_wake forces a render every second, so the whole model rebuilds every second. Separately, render_active_rows computes format_time_ago, a row-id String and up to four key strings for every row before the off-screen test, plus an O(rows × groups) group scan and per-frame set/retain/order work.
Why slow
Virtualization skips element content but not these per-row allocations, off-screen rows included. Cost scales with session count and is already documented as a per-paint cost in docs/performance-sidebar.md.
Fix
Move format_time_ago and the key strings below the off-screen split, cache them on the model row (they change only with the second or the row data), and key the model on derived statuses rather than the raw clock. The fingerprint itself could hash only fields that affect the drawn row.
06

Per-frame hashing and cloning in every visible transcript row

Medium
crates/ui/src/transcript.rs:8040-8045, 2614, 8700-8724 · crates/ui/src/syntax_cache.rs:26
What
render_row clones the row and clones the whole Theme per visible row per frame. For each visible code block it computes DocumentHighlightKey::new, which SHA-256 hashes the full code text, just to look up an already-cached highlight. The tokenization itself is correctly backgrounded.
Why slow
A constant factor, but applied to every visible row and code block at repaint rate, including on hover, scroll and animation frames. Repeated hashing of the same buffers.
Fix
Memoize the document key per (row, block) so it is computed when content changes, not per frame. Borrow or Arc the row instead of cloning it, and hoist the theme clone out of the row loop.
07

Command palette searches every chat on each keystroke and each hover

Medium
crates/ui/src/shell/command_palette.rs:637, 765-803, 1145 · crates/ui/src/shell/thread_search.rs:27-41
What
palette_sections is recomputed on every render, every arrow key and every mouse hover (hover_command notifies). thread_matches walks every chat, doing several linear scans and a format! per chat, and score_thread lowercases five fields per chat. Only workspace content search is debounced.
Why slow
O(all chats) with allocations per interaction. Hovering a result re-runs the whole search. Noticeable with a few hundred sessions.
Fix
Memoize sections by (query, tab) and drop the notify on hover (repaint only the hovered row). Lowercase the searchable fields once at chat-ingest time.
08

Render path does synchronous filesystem probes for inline code links

Medium
crates/ui/src/workspace_links.rs:120-131 · reached from crates/ui/src/transcript.rs:8183, 8217
What
PathProbes::kind calls std::fs::metadata during row render to decide if an inline-code span names a real file or directory. It is memoized per path per link-roots revision, and the cache is cleared when link roots change.
Why slow
On a cache miss (new streamed text, first paint of a part, link-roots change) each span does a blocking metadata syscall during layout. resolve_inline_code_path can probe several roots plus context dirs per span.
Fix
Precompute the probe results during background row preparation, or move misses to the background executor and render the neutral state until they resolve.
09

Caches that grow without eviction across a session

Medium
crates/ui/src/transcript.rs:2599, 3615-3619, 5180 · crates/ui/src/file_icons.rs:213-215
What
HighlightStore.entries is keyed by (row id, block index) and cleared only on chat attach. blob_details and blob_fetch_order hold full tool diff and output text and are never pruned. The file-icon raster cache is a process-global map with no budget.
Why slow
A long-lived window accumulates dead slots and retained payloads. blob_details even survives chat switches, since the attach reset does not include it. The rest of the caching in the crate is well bounded (syntax 96 docs / 24 MB LRU, formula cache, inline-link LRU), which makes these stand out.
Fix
Prune both maps on a row/attach sweep, and give the icon raster cache an LRU bound like the others.
10

Diff pane allocations per row per frame

Medium
crates/ui/src/changes.rs:3246, 3250, 3275, 3281
What
Each visible diff row clones parsed.key (a String), clones the theme, and builds two format!("changes-code-row-{ix}") element ids per frame. The patch parse and highlighting are correctly off-thread and keyed.
Why slow
Small allocations, but on a large diff this is a per-line, per-frame cost. The single-pass excerpt allocation (vec![Vec::new(); max_line] up to 200k) is on the background path, which is fine.
Fix
Borrow the parse key, hoist the theme clone, and build element ids with a reusable buffer or a cheaper stable id.
11

Branch inspection spawns six to eight git processes in series

Low
crates/engine/src/source_control.rs:1335-1436
What
GitCheckoutInspector::inspect awaits rev-parse, branch --show-current, rev-parse @{upstream}, two config --get, remote, remote get-url (twice) and symbolic-ref as separate process spawns.
Why slow
It is on the RPC path that resolves PR context. On Windows, process spawn cost is real. The chain is serial and can be collapsed.
Fix
Batch into one git for-each-ref or a single git status --porcelain=v2 --branch call, and reuse results for the PR lookup.
12

Two UI-thread parses per keystroke: composer markdown and git history

Low
crates/ui/src/composer.rs:4483 · crates/ui/src/history.rs:2153-2206
What
composer_markdown::faces runs a full pulldown-cmark parse of the draft on the UI thread whenever the composer reshapes (up to 128 KB), while syntax spans are backgrounded. History filters all loaded commits with per-commit to_ascii_lowercase and runs layout_graph twice (visible and all commits) on each keystroke.
Why slow
Both are per-keystroke and grow with draft size or commit count. The composer is gated by a layout key, so it is per reshape rather than per frame.
Fix
Move the composer face parse to the background executor alongside the syntax spans, and precompute a lowercase haystack per commit at load.

03What is already fast

Worth stating plainly, so the priority list above is read in context. These are the non-obvious things that are done well.

Transcript virtualization is real

gpui list() with a 320 px overdraw, row heights memoized by ListState. Streaming remeasures only the tail; a whole-list remeasure() is reserved for width, font or style changes, never a token.

transcript.rs:3789, 5543-5585, 11503

Markdown parses incrementally

The streaming tail re-parses from the second-to-last stable block boundary, completed blocks are shared by length, and highlighting plus row preparation run on the background executor.

crates/markdown/src/parser.rs:2100-2178 · transcript.rs:2605-2712

Bounded caches where it counts

Syntax documents are a 96-entry / 24 MB LRU, the formula cache is byte-bounded, the inline-link cache is an LRU, and the transcript render cache retains only the viewport plus overdraw.

syntax_cache.rs:14-16 · markdown/render.rs:443-509

Animation clocks are leased

The shared pulse clock runs at 30 Hz, small spinners at 15 Hz, and leases expire when hidden. The macOS renderer stops its display link when frame requests park, cutting idle wakeups by about 96% in the measured report.

motion.rs:206-273 · docs/performance-idle-presence.md

Workspace search is indexed

File and content search run on a per-root fff index with an idle-eviction lifecycle, cutting tree search from hundreds of milliseconds to low single digits on a large monorepo.

crates/engine/src/workspace_search.rs · docs/performance-workspace-search.md

Diff parsing is keyed and off-thread

The patch parse is skipped when the key is unchanged, runs on the background executor otherwise, and highlights per file by fingerprint. Only the per-row render allocations remain.

changes.rs:2348-2363, 3106-3237

04How to measure it yourself

The repo already ships the tooling. The findings above are from reading code, not from a benchmark run on this machine, so treat the ordering as a hypothesis to confirm.

ZERON_FRAME_STATS=1
Per-view render cadence, including sidebar frames per second. The right way to see issue 4 and 5.
ZERON_NO_RENDER_CACHE=1
A/B knob for the transcript flatten cache.
scripts/perf/resource-profile.mjs
The replay profiler used for the CPU and RSS reports. Drives a captured stream through the real window.
scripts/perf/profile-composer.py
Composer-focused CPU and memory profiler with real input events.
scripts/fixtures/resource-stream.jsonl
The 52 KB captured reply reused by most perf docs, at a fixed delta cadence.
ZERON_WHALE_SNAPSHOT
Runs the huge-transcript open and revisit test used to validate background preparation.
crate bench, engine
cargo run --release -p zeron-engine --example workspace_search_bench for the search index.
